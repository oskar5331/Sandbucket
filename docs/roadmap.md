# MVP Roadmap — Sandbucket

**Created:** 2026-11-01 · **Covers:** `prd.md` v1.0 (MVP)

This file sets **what is built, in what order, and when each part counts as done**. It does not restate decisions. Every `§N` points into the `prd.md` Decisions Log or its §6 scope sections, and `setup-config.md §N` points into that file. If a milestone and the PRD disagree, the PRD wins: fix this file.

Milestones are in dependency order and carry no dates. A milestone is done when every exit criterion holds **and is enforced by a test or a CI check**, not by a manual look, wherever §28 / §29 allow.

---

## Cross-cutting rules (apply to every milestone from M1 on)

These are standing obligations, not milestones. They come straight from the PRD, so they are only pointed to here:

- **New tenant-scoped table** ships with its RLS policy and per-table cross-tenant test in the same PR (§19, §28). Without them it is a review blocker.
- **New transaction type or action** ships with its posting unit test and its §6.20 role tests, both allowed and refused (§28).
- **Every user-facing string** goes through next-intl with an `en` key (§16). Estonian can lag inside a milestone, but must be complete before M11.
- **Initial JS ≤ 200 KB**, enforced by `size-limit` on every PR (§8, §29).
- **Mobile-first**: design at 390 px, Playwright phone projects first (§27, §28).

## M0 — Repo bootstrap & CI skeleton

**Goal:** an empty app that builds into the production Docker image, with every CI gate wired before there is code to guard.

- Create the `sandbucket` repo with the layout from §14. Move these docs into `docs/`.
- `package.json` pinned to the exact versions in `stack-versions.md`, with `packageManager` set to pnpm. ~~Confirm TypeScript 7 works with `next build`~~ Done 2026-11-02: the build works, but typescript-eslint doesn't support TS 7, so the project is pinned to 6.0.3 (`stack-versions.md`).
- `Dockerfile` (Node 26, `next start`, dbmate in the image) (§17, §29). *dbmate replaced by Prisma Migrate on 2026-11-04 (PRD §5, §18); the image now ships the Prisma CLI.* `fly.toml` moves to M11, since nothing deploys before then (Q2).
- `compose.yaml` with app, Postgres and Garage for local dev and self-host (§8, §17). The devcontainer reuses it.
- ESLint with the `no-restricted-imports` quarantine on `lib/db/unsafe.ts` (§12).
- GitHub Actions PR workflow: lint, typecheck, Vitest, Playwright against the built image, `size-limit`, schema drift check (§29; kysely-codegen until 2026-11-04, now `prisma migrate diff`). Each step may run against a trivial target for now.

**Exit criteria**
- [ ] `docker compose up` serves the placeholder page locally.
- [ ] A PR shows every §29 check running and green.
- [ ] Importing `lib/db/unsafe.ts` from outside its allowlist fails lint, proven by a fixture or test.

## M1 — Database, roles & tenant isolation

**Goal:** the isolation machinery exists and is proven *before* any business table depends on it. This is the security foundation, so it gets built first and tested hardest.

- `prisma/schema.prisma` and Prisma migrations in `prisma/migrations/` (§18). Postgres roles `sandbucket_app` and `sandbucket_owner` with the grants from §19.
- The shared `updated_at` trigger under the §4a carve-out. Audit columns per §7.
- better-auth tables, generated by its CLI and committed as a migration (§21).
- `profile` (§8 soft delete, §10 `currency_code`) and `profile_members` (§11, plus the owner partial unique index from §32), with their user-keyed RLS policies (§19).
- `lib/db/unsafe.ts` (owner handle) and `forProfile(profileId)` accessor (§19): transaction-local settings, membership check, `profile_id` injection on read/insert, stripping on update. The accessor exposes the member's **role**, so later milestones can gate actions (§6.20).
- **Reusable test harness**: a helper that, given a table, seeds two profiles and runs the §19 read/update/delete assertions both through the accessor and as a raw query on `sandbucket_app`. The aim is to make the per-table test a one-liner, so nobody is tempted to skip it.
- The shared "no settings → zero rows in every tenant-scoped table" test (§19). It must discover tables from the catalog, not from a hand-kept list, so that adding a table can't silently skip it.
- Prisma Client generated from the schema. The drift check (`prisma migrate diff`) now has real input.

**Exit criteria**
- [ ] Cross-tenant tests pass for `profile` and `profile_members`.
- [ ] Zero-rows test passes and fails if a policy is dropped (proven once by a deliberate break).
- [ ] Schema drift check (`prisma migrate diff`) passes in CI.

## M2 — Auth, profiles & app shell

**Goal:** a person can sign up, verify, sign in, and land in their own empty profile on a phone.

- Email + password, verification before first sign-in, password reset (§21, `setup-config.md §4.4`). `ALLOW_REGISTRATION` toggle (`setup-config.md §4.1`).
- `lib/email/send.ts` over SMTP (§22).
- Platform admin seed from `ADMIN_EMAIL` / `ADMIN_INITIAL_PASSWORD`. It aborts when either is unset (`setup-config.md §2`).
- First-login default profile, plus profile create (currency picker, §10) and profile switcher (§6.1). The profile seed runs on the owner handle (`setup-config.md §3`).
- next-intl wiring: `NEXT_LOCALE` cookie, Accept-Language fallback, typed keys, `messages/en.json` + `messages/et.json` (§16).
- shadcn/ui scaffold and §27 tokens (light and dark), the mobile app shell and navigation (§15, §27).
- Structured JSON logging to stdout (§30). It's cheap to add now and harder to retrofit.

**Exit criteria**
- [ ] Playwright (phone projects): sign up → verify → land in the default profile.
- [ ] Unverified users cannot sign in. Reset link is single-use.
- [ ] Switching profiles needs no re-auth and shows no data from the other profile.

## M3 — Ledger engine

**Goal:** the double-entry core, built and unit-proven with no UI on top.

- `Money` value object and its Zod boundary (§9, §13), plus the amount-input parser beside it (§16). The parser gets a unit test per rule: `.` and `,` both accepted, spaces ignored, mixed marks refused, too many decimals for the currency refused (EUR and JPY cases).
- `party` table with every column MVP needs, so later milestones don't migrate it again: type enum including `opening_balances` (§6.2), `is_system`/`system_key`, `is_group`/`parent_party_id` (§24), `custodian_party_id` + CHECK (§31), `linked_user_id` + CHECK + unique (§32), soft delete (§8). RLS and cross-tenant test included.
- `transaction_group` (type, `currency_code` + §10 guard, `linked_transaction_group_id` §26) and `record`, hard delete with cascade (§8). RLS and tests included.
- The nine posting handlers as pure functions from validated input to Records (§4 table, §25, §31), plus persistence through the accessor.
- Balance recalculation on save and delete (§4 "Balance"). Edit (description / date / amount only) and delete paths (§6.11).
- Zod schemas per type in `lib/schemas/` (§13).
- Seeding the system parties, including Opening Balances (`setup-config.md §3.2`), plugs into M2's profile seed.

**Exit criteria**
- [ ] §28 unit invariants: every group's Records net to zero, every balance equals the sum of its Records, and each of the 9 types posts the expected Records.
- [ ] Single-currency guard rejects a mismatched group (integration test).
- [ ] Cross-tenant tests pass for `party`, `transaction_group` and `record`.

## M4 — Parties

- Party list grouped by custodian (§6.19), create / edit / deactivate (§6.2), deactivating a register only at zero balance (§6.19).
- Party groups (§24) and system-default pre-fill (§6.2).
- Set Opening Balance, both at creation and later (§6.17, §25).
- Party balance view (§6.12).
- Role gating per §6.20: an accountant cannot deactivate, a worker cannot manage parties. Role tests per action.

**Exit criteria**
- [ ] Every §6.20 "Manage parties" cell has an allowed or refused test.
- [ ] Deactivating a register with cash still held is refused.

## M5 — Transactions

**Goal:** the core product loop and the §5 three-minute goal.

- Entry forms for all nine types (§6.3–§6.9, §6.17, §6.19), mobile-first, with the required money-source choice (§6.3/§6.4). The Withdrawal form auto-creates "Cash held by <name>" (§6.7).
- Transaction list: sign and colour rules, filters, search, pagination (§6.10). Invoice grouping comes in M6.
- Detail, edit and delete with role-scoped rights (§6.11, §6.20). The worker restriction (Expense only, own register or personal) is enforced in the accessor (§32).

**Exit criteria**
- [ ] Playwright: sign up → first transaction is a scripted journey (§5, §28). Timing it on a phone is an M11 check.
- [ ] One Playwright form test per transaction type (§28).
- [ ] Role tests for every §6.20 create and edit/delete cell, including worker visibility of their own entries only.

## M6 — Invoices & payments

- Invoice number and due date fields. Record payment pre-filled from the invoice, which links via §26.
- Computed payment status and Overdue. Grouped expandable rows in the "All" view. Open-invoices view with totals (§6.18).
- Overpayment refused. Delete and amount-lowering protection (§6.18).

**Exit criteria**
- [ ] Integration tests for status computation, overpayment refusal, and both protection rules.
- [ ] The "Money in" / "Money out" filters still add up to cash flow with payments present (§6.10).

## M7 — Attachments

- Attachment metadata table with RLS and cross-tenant test (§19). Presigned PUT/GET with 60 s TTL, minted only after the accessor read (§20).
- Client-side jSquash compression, HEIC fallback, 10 MB + MIME allowlist enforced at presign and in Zod (§6.13, §20, §23a).
- Camera capture and file upload. Images inline, PDFs and undecodable HEIC as download links (§6.13).
- Same code path against Garage (self-host and CI) and Tigris (hosted). CI uses real Garage, not a mock (S3Mock validates neither signatures nor CORS).
- §20 enforcement: signed `Content-Length` / `Content-Type`, then a `HeadObject` check before the key is saved. URLs signed against `S3_PUBLIC_ENDPOINT_URL`.

**Exit criteria**
- [ ] Playwright attachment journey (§28).
- [ ] A user of profile B cannot obtain a URL for profile A's attachment.
- [ ] Browser-level tests against Garage: upload and display succeed through CORS; an oversized upload, a wrong content type and an expired URL are each refused.

## M8 — Members & invitations

Role *gating* already exists from M4/M5, whose tests seed members directly. This milestone adds the way **real** second members arrive.

- `profile_invitation` with RLS, hashed single-use token and 7-day expiry, plus revoke (§32). Invite email through §22.
- Accept flow for existing users and for new users who sign up through the link (§6.20). Accepting runs on the owner handle (§19).
- Party link on acceptance (create or pick), "me" pre-fill, custodian resolution (§6.20, §6.19).
- Ownership transfer and remove / leave (§32).

**Exit criteria**
- [ ] Invite → sign up → join → worker records an Expense from their own register. One Playwright journey.
- [ ] Expired, revoked and reused tokens are refused (integration tests).
- [ ] The exactly-one-owner invariant holds across transfer (DB index plus test).

## M9 — PWA & offline

- Serwist service worker: app shell, static assets and the jSquash WASM cached on install (§6.16, §23).
- Manifest, icons, splash screens, update prompt (checklist "Low" item).
- Offline banner, blocked submits, form state preserved (§1, §6.16).

**Exit criteria**
- [ ] Lighthouse PWA ≥ 90 (§5).
- [ ] Playwright: going offline mid-form shows the banner, blocks submit, and keeps the input.

## M10 — Minimal platform admin

Scoped down from `setup-config.md §4.3` (decision 2026-11-01): MVP gets the seeded admin plus a **user list** (email, registration date, profile count, last active) and **disable / re-enable**. GDPR erasure, connect-to-tenant and platform metrics are post-MVP (see below).

- `/admin` routes, separate from app navigation. The admin data path goes through the quarantined handle (§12), and the lint allowlist is extended by name.
- A disabled user cannot sign in, and their existing sessions are revoked.

**Exit criteria**
- [ ] A non-admin gets refused at `/admin` (test).
- [ ] The admin sees zero tenant bookkeeping data (test).

## M11 — Launch readiness

- Provision Fly: app, Managed Postgres, Tigris. **Capture the Tigris keys at creation** (`setup-config.md §5`). Set secrets.
- Deploy on merge to `main` with `release_command` migrations (§29). GHCR image on `v*` tags for self-host.
- **Confirm Fly MPG backup retention and PITR** (§18, checklist "Low"). Write the self-host backup docs (`pg_dump` + object-store copy).
- Self-host README: Compose, env vars, SMTP.
- Estonian translation complete. A CI check that `et.json` has every `en.json` key keeps it from rotting.
- Privacy policy and ToS for the hosted version (legal).
- Measure the §5 success metrics on a real mid-range Android phone on throttled 3G: time-to-first-record < 3 min, bundle, Lighthouse.
- MIT `LICENSE` file, public repo (§5, §8).

**Exit criteria (= MVP done)**
- [ ] Every §5 MVP goal and success metric is met and recorded here, with the measurement.
- [ ] A fresh self-host from the README alone reaches a first transaction.
